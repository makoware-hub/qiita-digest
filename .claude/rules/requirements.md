# 要件定義ルール

このシステムに機能を追加・変更するとき、実装より先に「何を・なぜ作るか」を固定するためのルール。`docs/design/requirements.md` に書く内容の型と、書く際に気をつけることを定める。

## 位置づけと進め方

- `docs/design/requirements.md` は「実装で迷ったら立ち返る」拠り所であり、設計・実装・テストの各フェーズはここに書かれたスコープと受け入れ基準を前提に進める。
- 既存サービスの変更であれば、まず `docs/design/requirements.md` の該当セクションを読み、現状の要件との差分を意識してから書き足す。新規サービスであれば、このファイルに新しいセクションを追加する。
- 要件が固まったら設計フェーズ（`.claude/rules/design.md`）に引き継ぐ。要件が曖昧なまま設計・実装に進まない。

## requirements.md の章立て

サービス（または変更）ごとに、以下の項目を満たすセクションを作る:

- **背景・目的** — なぜこの機能が必要か。誰が困っていて、何を解決するか。
- **スコープ** — やること・やらないことを明記する。「やらないこと」を省略すると、設計・実装段階で際限なく範囲が広がる。
- **機能要件** — 実現する振る舞いを箇条書きで列挙する。
- **非機能要件** — 実行頻度・想定件数・レイテンシ許容度・コスト上限など、数値で書けるものは数値で書く。
- **制約** — 外部サービス（Qiita API・Bedrock）のレート制限やモデルアクセス条件など、設計の前提となる制約。
- **受け入れ基準** — 「何がそろえば完了と言えるか」をテスト可能な形で書く（結合テストのシナリオの元になる）。
- **オープンな論点** — この時点で決めきれないことは、決めきれないまま書き残す。設計フェーズで判断する。

## 書くときに気をつけること

- 曖昧な「〜な感じ」「たぶん〜」を残したまま次のフェーズに進まない。決めきれない場合は「オープンな論点」に明示的に残し、なんとなく決まったことにしない。
- 外部サービスの制限値（Qiita API のレート制限、Bedrock のクォータ等）を記憶で書かない。CLAUDE.md の共通規約と同様、aws-knowledge MCP や一次情報で裏取りし、出典を併記する。
- 要件定義の段階では実現方法（どの AWS サービスをどう組み合わせるか）に踏み込まない。それは設計フェーズ（`.claude/rules/design.md`）の領分であり、ここで先取りすると設計の選択肢を不必要に狭める。

## 変更管理

- 既存機能の要件を変更する場合は、該当セクションを書き換えるだけでなく、変更内容と変更理由を残す（後から「なぜ変えたか」が追えるようにする）。
- 要件変更が設計・実装済みの範囲に影響する場合は、影響するサービス名を明記し、設計・実装の各フェーズで追従が必要なことがわかるようにする。

## 次のフェーズへ

要件が固まったら、設計フェーズで `docs/design/architecture.md` 等へ落とし込む。技術的な実現可能性の検討はそちらで行う。
